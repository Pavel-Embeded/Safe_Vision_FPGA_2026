# 阶段 6–7 板级验收：电脑侧基准（expected UART report）
# ---------------------------------------------------------------------------
# 条目：evidence/board/INDEX.md 的 REF-STAGE6
# 日期：2026-10-02
# 用途：与 `top_stage6_fat32_mount` 上板后经 UART 发出的 ASCII 报告**逐项对账**。
#
# ★ 这份基准是电脑侧【独立】算出来的，不依赖 FPGA 的任何输出：
#   输入 = 已归档的卷引导扇区 `evidence/board/lba8192_pc_20261002.bin`
#          （512 B，SHA-256 e470416567d512c0…，即物理 LBA 8192）
#   方法 = 按 FAT32 BPB 字段用小端解析后作纯算术推导。
#
#   可靠性分级（重要）：
#   · 【硬推导】几何段（MBR/BPS/SPC/NFAT/FATLBA/DATALBA/ROOTLBA/TOTSEC/TOTCLUS）
#     全部由上面那个已归档的 512 B 推出，可复现、可核对，**权威**。
#   · 【记录值】目录项段（E 行）来自 2026-10-02 当时用卷句柄读到的根目录内容记录。
#     **原始根目录扇区当时没有归档**（卡已从读卡器取下，无法补读），
#     所以这几行是"预期值/待确认"，权威性低于几何段。
#     上板报告出来后，以它为准回填，并把原始扇区补档。

# ===========================================================================
# 一、已归档 DBR 的字段（小端解析）
# ===========================================================================
# OEM        = "MSDOS5.0"
# BytsPerSec = 512        (0x0200)
# SecPerClus = 8          (0x08)
# RsvdSecCnt = 2526       (0x09DE)
# NumFATs    = 2          (0x02)
# TotSec16   = 0          (用 TotSec32)
# HiddSec    = 8192       -> 与 Get-Partition 的分区起始扇区一致（自证）
# TotSec32   = 15515648   (0x00ECC000)
# FATSz32    = 15121      (0x3B11)
# RootClus   = 2

# ===========================================================================
# 二、硬推导的几何（FPGA 报告的几何段必须与此逐项相同）
# ===========================================================================
# 推导式：
#   fat_lba   = RsvdSecCnt
#   data_lba  = RsvdSecCnt + NumFATs * FATSz32
#   root_lba  = data_lba + (RootClus - 2) * SecPerClus
#   total_clus= (TotSec32 - data_lba) / SecPerClus      <- 整除，余数 0
# 交叉校验（全部通过）：
#   HiddSec == 分区起始 8192                    -> True
#   data_lba == 32768 (0x8000)                  -> True
#   fat_lba  == 2526  (0x9DE)                   -> True
#   root_lba == data_lba                        -> True（RootClus=2，根目录就是数据区第一簇）
#   total_clus * SecPerClus + data_lba == TotSec32  -> True（余数 0）

# ===========================================================================
# 三、期望的 UART 报告（ASCII，CRLF 行尾；这就是要逐项对的基准）
# ===========================================================================
SAFEVISION B STAGE6
MBR=00000001 BASE=00002000 SECS=00ECC000
BPS=0200 SPC=08 NFAT=02
FATLBA=000009DE DATALBA=00008000 ROOTLBA=00008000
TOTSEC=00ECC000 TOTCLUS=001D8800
ENT=0005
E 0009 5356303030352020424D50 20 00000600 000E1036
E 0019 5356303030312020424D50 20 0000E800 000E1036
E 001A 5356303030322020424D50 20 0000CA01 000E1036
E 001B 5356303030332020424D50 20 0000AC02 000E1036
E 001C 5356303030342020424D50 20 00008E03 000E1036

# ★ 2026-10-02 第二版（加入连读阶段 M-6 之后的格式）：
#   报告多了 `RPT=<总次数:4hex> OK=<成功:4hex> BAD=<失败:4hex>` 一行，在 E 行之后、
#   DONE 之前；实卡（5 项）总长约 **476 Byte** = 183（头）+ 5x52（E 行）+ 27（RPT 行）+ 6（DONE）。
#   连读失败时末行由 `DONE` 变为 `ERR=02`（`RPT` 行照发）。

# ★ 2026-10-02 上板回填更正（以实物为准）：
#   ① `ent_index` 是【0 起始】的目录槽号。本文件初版写的是 000A/001A/001B/001C/001D，
#      那是按"第几个表项"从 1 数起的记法，**写错了**；实物报告给的是
#      0009/0019/001A/001B/001C，与 1-based 记法相差 1，**实物正确**。
#      （即：0-based 槽 9 是 SV0005，槽 25/26/27/28 是 SV0001–SV0004。）
#   ② 实物报告每行以 `72 0A`（字母 r + LF）结尾，而不是 `0D 0A`（CR + LF）。
#      ★ 更正（2026-10-02，vlog 实测后）：**Verilog-2001 的转义表里没有 `\r`**
#      （只有 `\n` `\t` `\\` `\"` 和八进制 `\ddd`），所以 `"...\r\n"` 在
#      **TD 与 ModelSim 里都**编成 `72 0A`（字母 r + 换行）—— **不是两者不一致**。
#      本文件初版把原因判成了"TD 不处理转义、ModelSim 是 0D"，**判错了**，已更正。
#      老 TB 之所以通过，是因为 TB 用了同一个错误转义构造期望值，**两边错得一样**。
#      修法：写显式字节 `8'h0D, 8'h0A`（已改）。属**纯外观瑕疵**，不影响判定。

# ===========================================================================
# 四、逐项解释（对账时按这张表看）
# ===========================================================================
# MBR=00000001 : 扇区 510/511 = 55 AA 且分区项有效（has_mbr=1）
# BASE=00002000: 分区 0 起始物理 LBA = 8192  <- ★ 整件事的核心：
#                FAT32 层的"卷 0 号扇区"必须落到卡的 8192，而不是卡的 0
# SECS=00ECC000: 分区长度 15515648 扇区（MBR 分区项 offset 446+12..15，小端）
# BPS=0200     : 每扇区 512 字节
# SPC=08       : 每簇 8 扇区（4 KB）
# NFAT=02      : 2 个 FAT
# FATLBA=000009DE : FAT1 起始（卷内相对 LBA）= 2526
# DATALBA=00008000: 数据区起始 = 2526 + 2*15121 = 32768
# ROOTLBA=00008000: 根目录起始（= DATALBA，因 RootClus=2）
# TOTSEC=00ECC000 : 总扇区 15515648
# TOTCLUS=001D8800: 总簇数 1935360
# ENT=0005     : 扫到 5 个**文件**目录项（目录项 / LFN / 已删除项不算）
#
# 目录项格式：E <ent_index> <11 字节 8.3 名 hex> <ent_attr> <ent_first_clus> <ent_size>
#   5 行都是 0x20（归档标志），size = 0x000E1036 = 921654 = 640*480*3 + 54
#   （640x480、24bit、无压缩 BMP 的标准大小 —— 对得上就说明读的是真图）
#   顺序按**目录槽号**递增：槽 10 是 SV0005，槽 26–29 是 SV0001–SV0004。
#   （卡上还有 20 个 0xE5 已删除项与 1 个 `System Volume Information`，
#    它们应被 scanner 跳过、不出现在 E 行里 —— 这也是要确认的行为。）
#
# ★ 另外要确认的：SV0005.BMP 是**故意做坏的**那张（文件头前两字节被改成 FF FF，
#   正常应是 "BM" = 42 4D）。阶段 7 的坏图测试是"能扫到但不装载"，
#   本阶段的扫描报告里它**应该照常出现**（本步只验目录扫描，不验 BMP 头）。

# ★★ 2026-10-06 更正（重要，缺陷 24）：上面 E 行的 `ent_first_clus` 是**字节交换**后的值
# ===========================================================================
# 事实：那 5 个值 `00000600 / 0000E800 / 0000CA01 / 0000AC02 / 00008E03`
#       按 16 位交换后是 `6 / 232 / 458 / 684 / 910` —— **差值恰 226 簇**
#       （= ceil(1801 扇区 / 8 扇区每簇)），正是真实 FAT32 顺序分配的形态。
# 根因：`fat32_directory_scanner.v` 把目录项的 FstClusHI(0x14-0x15) / FstClusLO(0x1A-0x1B)
#       按**大端**装配，而 FAT32 这两个字段是**小端** ⇒ 真卡（Windows 写）上首簇全部交换。
# 影响：卡→屏链首次上板失败（`EC=03`，读的是错地址）——见 evidence/board/INDEX.md
#       的 SVPLAY-CAP-01 与 docs/方案A-第二轮复核交接.md §2.3。
# 说明：本文件 E 行的 first_clus 段本来就是"待上板报告回填"（见文件头【记录值】说明），
#       回填的是**板子自己的输出**，所以自证循环、看不出这个错。**不要拿它当正确值对账**。
# 状态：RTL 与仿真卡模型（`sd_spi_card_model.mk_dir_entry`，同款错序）均已改回小端，
#       `tb_fat32_directory_scanner` 57/0、整链 TB 17/17 通过；待重新出位流上板复测。
