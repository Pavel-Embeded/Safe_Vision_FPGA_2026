# 项目管理规则

## 工作项流转

`计划 → 接口/设计评审 → RTL 与 TB → 单元通过 → 子系统通过 → 综合/STA/CDC → 上板 → 实测 → 冻结`。手册 V2.0 §4.4/§11.7 的“计划 / 已仿真 / 已综合 / 已上板 / 已实测 / 已冻结”是对外报告状态；中间评审是团队内部步骤，不得把仿真通过写成实测通过。

每个工作项记录：需求编号、负责人、复核人、源文件、接口编号、测试编号、验收标准、证据路径、当前状态、阻塞项。优先 B01–B04 主链，再做 E 项。具体下一步见 [WORK_ITEMS](WORK_ITEMS.md)。

## 分支、提交与评审

- 功能分支按 `feat/<模块>`、修复按 `fix/<问题>` 命名；一个 PR 聚焦一个接口或一个可测试功能。提交信息建议 `A(video): ...`、`B(storage): ...`、`C(safety): ...`，引用需求/测试编号。
- 改跨人接口：先在 `docs/interface_spec.md` 写差异（七字段、时钟、CDC、异常/复位），A/B 或 A/C 双方评审并更新 TB，再改 RTL。评审记录放 `docs/management/adr/` 或 PR。现有 B 规范是基线，不能单方重写。
- PR 必须含变更范围、测试命令/结果、未验证项、证据链接、回滚办法。影响安全路径或复位时，A 与 C 双人复核；影响内存/视频接口时，A 与 B 双人复核。
- 不把工具生成物、厂商例程和本地手册直接提交。许可及借鉴来源登记 `evidence/provenance/`。

## 冻结与集成

每次联调只引入一个变量，按 `docs/verification/README.md` 的 I0–I10 阶梯推进。准备联调前，接口规范可定位到同一 Git 提交，三条链各能单跑。每次候选版本记录 Git 提交、文件清单、工具/IP 版本、约束、测试结果与已知问题；若回归失败撤销候选，不抬高状态。

目录决策见 [ADR](adr/0001-layout.md)，分工见 [ownership](ownership.md)，重要变更见 [CHANGELOG](CHANGELOG.md)。
