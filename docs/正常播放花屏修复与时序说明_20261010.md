# 正常播放花屏修复与时序说明（2026-10-10）

> 本文保留 `ID=26101001` 的历史结果。多轮验证发现并修复了 BMP 文件头晚于开帧时的方向锁存问题；当前交付请使用 `ID=26101002`，见 [A/B 多轮验证与修复说明](A_B多轮验证与修复说明_26101002.md)。旧位流、旧时序数值不作为新版验收证据。

本轮针对：上一版 BASE 位流下，图片短暂出现后变白，按下一幅时花屏；黄色/红色 Exit 能正常显示。基线为 `7d99493eaba837192d45a3ce7647aa78895c1949`，独立分支为 `codex/normal-playback-integrity-fix-20261010`。原分支、原下载文件和队友其他模块保留。

## 1. 判断依据与不确定性

照片能辨认主体、却出现随机彩色短条，符合像素数据丢失、错位或损坏的表现。Exit 正常，意味着它使用的片内图形路径及 HDMI 基本扫描能工作，因此优先排查正常图片独有的 SD→BMP→SDRAM→DMA→FIFO 路径。它不能单独证明某一根 DQ、某一次刷新或某一个 IP 必然有错。

上一轮已修复“仲裁授权被当成每字写完成”，并增加物理写排空和换帧屏障；这些修复保留。但上一轮写侧 CRC 只比较生产者和写总线，没有证明 SDRAM 保存和读出了相同数据。应用接口模型也不会自己产生电气采样或保持错误。当前工程补上实际读回及显示前校验，并增加可定位的故障报告。

用户提到的 −5.08 ns 没有附起点、终点和原报告。仓库文本历史检索未找到这个精确数值；能核实的旧记录包含原 125 MHz 工程的 SDRAM setup −6.826 ns。不能把两个数字当成同一条路径，也不能据此断言“官方 IP 固有且无法修复”。

## 2. 正常图片现在怎样流动

```text
SD 扇区 CRC16 → FAT32/BMP 解析 → 32/16 异步 FIFO
  → 行序重映射 → 仲裁器实际接受的 32 位字
      ├─ SDRAM 写入
      └─ 地址/字数检查 + 每 64 字 CRC32 → 片内双端口校验表
  → 写缓冲和物理写尾排空
  → 读回新图片的全部 153600 字，与 2400 块源 CRC32 比较
  → 全部通过才发布帧槽 → 垂直消隐时切换
  → 每次显示：64 字读入落地缓存 → CRC32 通过 → 像素 FIFO → HDMI
```

每张图片为 640×480 RGB565，共 307200 像素、153600 个 32 位字。每块 64 字，即 128 像素；一张图片共 2400 块。一个图像行有 320 字，恰为 5 块，因此 BMP 自下向上行序不破坏块内像素顺序。

源校验值在 `prod_word_accepted` 时形成：`prod_wr_busy && mem_req && mem_wr && mem_ready`。CRC32 使用 IEEE 反射多项式 `0xEDB88320`、初值 `0xFFFFFFFF`、末尾取反，字节顺序为每个字的低字节先。测试用 Python `zlib.crc32` 的独立结果核对，而不复用 DUT 的 CRC 函数作为判定依据。

源检查还验证：合法槽号只为 0/1，写地址严格按指定行序推进，恰好接受 153600 字。开新帧和公共复位会清除对应有效标记，片内 RAM 的旧内容不能单独获得发布资格。

两个图像槽继续交替使用：槽 0 为字节地址 `0x00000000`，槽 1 为 `0x000A0000`。当前显示槽不会被下一张图覆盖。校验表端口 A 服务显示；端口 B 在写帧时写校验值、写完后读校验值。两阶段不重叠，故只需一份双端口 RAM。

### 并发播放的水位问题

本轮 720p 压力测试实际发现：视频正在显示时，快速写下一张图会出现一次 underflow。旧仲裁器的“缓存充足”阈值只有 48 像素，适合早期小缓存，却不足以保护当前扫描链。

板级校验模式改为：高水位 3600 像素、关键保护水位 3000 像素。视频 DMA 活跃且低于关键水位时，待处理视频读先获服务；DMA 准备下一块的请求空档中也不新启动写事务，否则缓冲写会增加一次物理写尾/静默间隔，仍可能断流。视频 DMA 空闲时以 MEM 域空闲标记解除保留，允许上电首帧写入。到突发边界才切换，不在突发中改主人。写端遵守 `ready` 反压，SD 端也必须能暂停。低水位保护暂时高于常规防独占策略；实际正常读带宽足够时水位回升，写端仍有服务机会。旧 B 实验接口仍采用 48/0 默认值。

后台整帧读回只在存储域 DMA 已空闲或水位至少 3000 时开始新块。这里使用 MEM 域状态，不直接使用 PIX 域 `active`。开发过程中真实 STA 曾抓到后者带来的 −3.292 ns；已修复跨域逻辑，没有将其设成假路径，违规候选没有生成位流。

## 4. 存储和 SD 时钟、刷新

板载输入仍是 50 MHz。系统 PLL VCO 为 1 GHz，C0 分频 10 得 SYS 100 MHz；C1/C2 分频 25 得 MEM/SDRAM 40 MHz。C1 CPHASE 为 24，C2 为 9，最终由 TD `derive_clocks` 和布线报告确认 SDRAM 上升沿在 10 ns，周期 25 ns。不是仅凭 GUI 相位标签推断。

SD 初始化仍为 100 kHz，正常读卡 SPI 分频默认为 1，对应 12.5 MHz。旧 BASE 的默认分频为 0；降速增加 MISO 采样余量。SD 扇区原本已有 CRC16，保留原校验和错误处理。

公开 EM638325 数据手册规定 4096 次刷新/64 ms。本板级宏使用 `SAFEVISION_REFRESH_ROWS=4096`，在 40 MHz 下得到 `64000000 / 25 / 4096 = 625` 拍，即约 15.625 µs 的保守刷新间隔参数。原实验默认按 `ROW_WIDTH=11` 的表达式保留。没有因此认定原 IP 一定刷新不足：加密内部可能在一次间隔内发多个命令，当前接口模型不验证其内部刷新实现。

参考：[Etron EM638325 Rev.3.2 数据手册](https://etron.com/wp-content/uploads/2022/04/EM638325_Rev-3.2.pdf)。它也给出器件真实的数据访问和建立/保持要求，例如 CAS=2 的访问时间上限为 6.5 ns。访问时间不是可随意删除的“占位延时”。

## 5. −5 ns 影响与本轮实际时序

如果原报告的 −5.08 出现在 Slack 栏，它表示数据相对采样要求少了约 5 ns 的裕量。这很大，足以产生不稳定数据；即使某次上板恰好成功，也不能登记为时序闭合。如果它是 PLL phase/latency 的设置数值，则必须结合报告路径解释，不能只看负号判定。

正确处理应先区分：跨域控制信号、用户组合路径、SDRAM 写出路径、SDRAM 读回采样路径、加密内部路径。分别采用同步器/邮箱、真实流水线、正确频率与相位、器件访问预算、官方器件/工具支持。不要直接删除器件访问时间，不要给 DQ 加全局假路径，也不要给每拍接收的数据随意增加多周期例外。

本轮所有 CRC32 反馈按一个 MEM 周期计时。已经被综合消除的生产模式回落图案不再套用旧 `fb_writer/crc_src` 多周期例外；检查器改为验证 32 个真实源 CRC 状态存在。UART `ridx` 的两周期约束保留，因为它的字节选择确实经过两拍协议采样。FIFO 及邮箱例外只作用于已定义的跨域/异步复位机制，SDRAM 数据路径继续计时。

最终真实布局布线结果如下；本包 `validation.json` 和 `BASE/720p/timing.gate.json` 保存原始数值。两种模式都满足 `timing_passed=true`、`negative_path_count=0` 后才生成位流。本包还保存完整 `route.timing`、时钟、例外、健康检查和构建输入哈希。

| 模式 | 最差建立裕量 SWNS | 最差保持/移除裕量 HWNS | 报告负路径 |
|---|---:|---:|---:|
| BASE | +1.563 ns | +0.011 ns | 0 |
| 720p | +0.396 ns | +0.010 ns | 0 |

最小正裕量并不等于很宽裕的板测容差；BASE 更适合作为第一轮上板入口。片内 RAM 为 54/64 块；BASE LUT 为 12896/19600。加密 IP 的物理编译使用本机 TD 6.2.168116。

BASE 位流 SHA256：`19856a42ecfd565b463c3c198515d346d99eac9df96b832babd02701ec22bf0e`。

720p 位流 SHA256：`17a6b0e186e1a31c8a0d52f4faa047cf343452a9b162e45d6d248c4e53bd99cb`。

## 6. UART 如何定位实际板上的问题

串口为 CH340、115200、8N1。原 107 字节 `SV-PLAY` 行保留；每个报告包紧跟一行 82 字节：

```text
SV-MEM ID=26101001 PH=2 BAD=00000000 EXP=00000000 GOT=00000000 W=00025800 B=0960
```

第二行的字段在报告包开始时统一取 MEM 域快照。已专门测试：发送第一行后改变实时 BAD/EXP/GOT，第二行仍保持包起点的值。

| 字段 | 含义 |
|---|---|
| `ID=26101001` | 本轮工程标识；配合 BASE/720p 位流 SHA256 确认下载版本 |
| `PH=0` | 尚未完成读回，空闲或正在写入 |
| `PH=1` | 等待/执行整帧读回 |
| `PH=2` | 新帧全部读回通过，允许发布 |
| `PH=3` | 源地址/长度检查、整帧读回校验或响应超时失败 |
| `PH=4` | 发布之后的播放块校验或响应超时失败 |
| `BAD` | 首个出错块字节地址；源顺序错误时为出错写地址 |
| `EXP/GOT` | 读回/播放错误为预期和实际 CRC32；源顺序错误为预期/实际地址 |
| `W` | 当前帧实际接受的源字数，完整帧为 `00025800` |
| `B` | 当前帧通过读回的块数，完整帧为 `0960` |

如 `PH=3` 且 `W` 不完整，优先看源地址、长度和写端握手。如 `W=00025800` 但块校验失败，则数据在源校验点之后的存储/读回路径发生差异。如第一次读回通过，之后 `PH=4`，应重点检查运行中读采样、保持、刷新和供电等问题；依然不能只凭 CRC 判断是哪根信号。

`BAD/EXP/GOT` 不表示单个坏 bit 已定位，CRC32 也存在碰撞概率，不是所有物理故障的数学保证。

响应超时意味着没有收齐所需数据，此时 `GOT` 可能保留此前的完整块结果，不能将它当成超时块的完整 CRC。需结合第一行 `SV-PLAY` 中的存储/播放状态和错误码一起判断；无论是 CRC 不符还是响应丢失，都先停止坏块输出并进入安全显示，而不根据不完整数据继续播放。

## 7. 验证与使用

`evidence/normal_playback_20261010/validation.json` 列出实际完成的测试及原始日志哈希。验证覆盖：源/读回/播放 CRC，完整 BASE/720p 画面、两个不同图像的手动切换、自动播放、写入当前显示槽的禁止条件、物理排空后发布、FIFO underflow/overflow、SOF/EOL、存储数据注入损坏后的红色 Exit，以及 KEY1 公共复位重新写入并读回。

| 模式 | 逐像素检查的完整显示帧 | 精确匹配像素 | 健康段 underflow/overflow | 未排空就发布 |
|---|---:|---:|---:|---:|
| BASE | 28 | 8601600 | 0/0 | 0 |

每种模式均完成四次手动/自动图片发布，再注入实际存储字损坏、确认红色 Exit，最后公共复位并重新写入、整帧读回、发布第五次图片。本长链用例在复位后第五次发布成功时结束，不将该阶段额外计作完成了复位后的逐像素扫描。故障注入后停止坏块可能产生安全像素/断流；720p 诊断监视器还在复位清零时打印计数变化，均与健康播放段单独判定。
