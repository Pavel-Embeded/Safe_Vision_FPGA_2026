## 五、★ 一条备注：让集成测试"从卡上的真文件取数"（不是 TB 造数据）

### 现状（你 5b54072 的做法）

你的 `tb_safevision_core` / `tb_ab_frame_display` 用 **TB 合成的 BMP 字节流**喂 `bmp_parser`
（`px24(x,y)` 现算），再用同一个函数算期望 —— 这对**验证显示链**是完全够的 ✓
（而且你加了 `MUTATE_COLOR` 变异、`HD`、`SUBMIT_LEAD` 参数，比我当初做的更强 ✓）

### 差别在哪

我另做过一条：**把真文件内容完整写进 SD 卡模型，让它从卡里读** ⇒
`sd_initializer → sd_sector_reader → mbr_parser → fat32_boot_parser → fat32_directory_scanner
→ file_index → file_streamer → bmp_parser → bmp_unpack → frame_writer → …`

**它多证明了一件事**：**"卡上那 921654 字节"到"屏幕 307200 像素"中间**，
`file_streamer` 的**簇链遍历**、`bmp_parser` 的**头部/行序**、以及**字节序**全对 ——
也就是**TB 造数据那条路覆盖不到的前半段** ✓

### 关键技术点（要复现只需两点）

1. **卡模型的卷要够大**：`sd_spi_card_model` 原卷窗口是 **64 扇区（≈32 KB）**，装不下
   640×480×24bit BMP（**921654 字节**）⇒ 我给它加了 `VOL_SECTORS` 参数（默认放到 **2048 扇区 = 1 MiB**）；
   **默认 `VOL_BASE=0` 的行为不变**，所以既有 TB 不受影响 ✓
2. **`frame_writer` 的 `GAP_TIMEOUT` 必须放大到能跨过一次 FAT 读**：
   真卡取数时每个**簇边界**要读一次 FAT 扇区，CMD17 停顿约 **16384 个 `clk_mem` 拍（131 µs）**，
   远超默认 512 拍 ⇒ **会误报"上游断流"** ✗。
   ★ 你已经在 RTL 里把 `GAP_TIMEOUT` 位宽改成 32 位（`frame_writer.v`）✓ ——
   **正是为解决这一类问题**，方向完全一致 ✓（我那版是只在 TB 里实例化大值，不如你的改法）

### 建议

- **这条"从卡取数"的路子值得并进你的集成 TB**：它能把"**SD/FAT32 前段**"也纳入整机回归 ✓
- 做法上：**卷扩大到 2048 扇区 + 把 `GAP_TIMEOUT` 实例化为 ~500_000**（我已验证可行）
- 我那份实现在**本地分支** `backup/card-to-screen-merge`（提交 `2e97790`）；
  因为和你 5b54072 的改动（你重写了 `tb_ab_frame_display`、也动了 `sd_spi_card_model`）**正面冲突**，
  我**按约定没有合并、也没推送** ✓ —— 你若要参考，说一声我把该分支推上去 ✓

★ 诚实边界：这条测法里卷仍是**合成的微型 FAT32 镜像**（1 个 FAT 扇区、32 扇区/簇、声明 2048 扇区），
