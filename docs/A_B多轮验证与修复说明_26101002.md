## 1. 本轮实际发现并修复的两个问题

这两个问题由本轮 RTL 测试复现并修复。原照片对应的旧位流仍缺少匹配的板上诊断，尚不能断言它们就是原始花屏的全部根因；本版提供可区分源、存储读回和播放错误的诊断与对应验证。

### 1.1 BMP 的行方向知道得比开帧晚

播放控制器先启动一帧，再读取 BMP 文件头。旧完整性检查器在启动时就记下 `top_down`，但此时它可能仍是上一张图的值；写入桥则在真正接受第一个像素时才记下方向。两者不一致时，合法图片也可能被判定为地址错误并进入安全显示。

`frame_integrity_guard.v` 现在用第一个实际接受的写字确定方向和起始行；此后只按锁存方向推进地址。槽基址仍在开帧时确定，不随实时输入改变。覆盖两个槽、正负 BMP 高度、开帧后才改变文件头结果、源暂停和不同响应节奏。

用上一版 27cb139 的检查器单独运行同一个“文件头晚到”用例，确实触发 `complete top/bottom image in either slot verifies` 失败；当前检查器通过。旧文件只从 Git 取入隔离的测试目录，没有回写产品源码。证据为 `header_negative.json` 和 `header_old_release_negative.log`。

### 1.2 720p 在较长读响应延迟下会断流

只修方向问题后，完整 720p 卡播放在 `RD_LAT=11` 时实际出现 underflow。旧读缓存只有 16 字，等客户端取完、发下一突发、收齐响应，再提供数据。即使平均带宽看似够，显示窗口中的连续需求仍会耗尽像素 FIFO。

`sdram_app_adapter.v` 增加可选 `PREFETCH_READ`，板级启用，原实验默认关闭。缓存成为两个各 16 字的缓存区：客户端取已完成的一半时，另一半预读下一连续块；必须收齐该块的全部响应才公开。读响应收集与物理命令后的静默计数并行，但仍保留至少 16 个静默时钟；连续物理突发不被中途打断，读写命令不重叠，单字写仍带一个全部屏蔽的邻字拍。

任意写请求会使读缓存失效。特别检查了“预读还在进行，出现一个尚未接受的写请求，随后取消”的情况：缓存必须从新的完整缓存区重新建立头指针，不能把新数据拼到已经失效的旧队列。该边界已修复并通过独立数据顺序检查。已接受的缓冲写仍须实际排空后才能发布图片，预读的尾部也不会绕过排空屏障。

在 40 MHz 存储时钟下，连续 4096 字、响应延迟 11 拍的实测模型结果为 9226 拍，即约 17.76 百万字/秒；720p 内 640 像素图片窗口每行需 320 字/22.22 µs，约 14.4 百万字/秒。这个数字说明接口实现的服务率，不是加密控制器或板卡电气性能的实测。最终完整卡用例另行检验读写并发、帧内峰值和 FIFO 水位。

## 2. 保留的项目数据通路与职责

```text
SD 读扇区 / FAT32 四图索引 / BMP 解码
  → 异步 FIFO → BMP 行序桥 → 仲裁器实际接受的写字
  → SDRAM 写缓存 → 物理写出与静默尾排空
  → 全图 153600 字读回、逐块 CRC32 比较
  → 只发布完整正确的非显示槽 → 帧边界切换
  → 显示块读入并校验 → 像素 FIFO → HDMI B
```

640×480 RGB565 图像每槽为 153600 个 32 位字，2400 个 64 字校验块。槽 0 字节基址 `0x00000000`，槽 1 为 `0x000A0000`。当前显示槽不得被写入；读回未通过不得发布；播放坏块不得进入像素 FIFO。公共复位重新开始槽所有权和校验资格。故障后的 Exit 使用片内图形，保持视频扫描运行。

前版的实际接受握手、物理排空、邮箱原子发布、垂直消隐切换、FIFO 水位保护、整帧读回和运行中块校验均保留。没有改写或解密官方 SDRAM/HDMI IP，也没有给 SDRAM DQ 增加全局假路径。原实验用 PLL、回环工程、B/C 队友模块和既有历史证据保留；新增 `protected_blobs.json` 对本次允许修改范围以外的每个基线 Git blob 做核对。

## 3. 测试为何能发现问题

本轮还修正了测试本身的三个缺口，避免把一个容易通过的模型当成验收。

- 读延迟为 1 时，原契约模型使用了负的位切片范围，改成移位形式，测试支持的 1～64 拍延迟都能正确建模。
- 第二个坏块响应很快时，前一个已校验块可能尚未全部输出便进入故障状态。测试改为核对实际输出是精确的正确前缀、最多 128 像素，且坏块没有任何像素输出，不再错误地要求上一块必定排完。原失败日志保留在 `diagnostics/old_fast_response_oracle.log`。
- 四个目录项原来共用同一图片和簇链，选错文件也可能通过。最终卡模型改为四幅颜色不同的图片、四条独立的 57 簇链，第三条跨 FAT 第 1/第 2 扇区；逐字和逐像素判定核对当前文件和帧代号。复位后重新启用判定，必须再完成两幅完整显示帧，不能仅以第五次发布为恢复成功。

测试图片 RGB 三通道和行列高位都变化；RGB565 色差常量独立预计算。CRC32 用独立 Python `zlib.crc32` 结果核对。原厂可读 FIFO/ERAM RTL参加相关仿真。168 份日志的构成如下：

## 4. 本版真实时序与约 −5 ns 的解释

最终原厂 TD 6.2.168116 从真实 `safevision_top` 编译，包括原加密 IP，冻结 114 个构建输入的 SHA256，确认构建后源码未变，再在严格门禁通过后生成位流。

| 指标（ns） | BASE | 720p |
|---|---:|---:|
| 全局 SWNS（含恢复检查） | +0.448 | +0.644 |
| 报告的数据建立最小余量 | +0.448 | +0.961 |
| 报告的数据保持最小余量 | +0.004 | +0.030 |
| 报告的恢复最小余量 | +3.584 | +0.644 |
| 报告的移除最小余量 | +0.003 | +0.003 |
| 报告负路径 / 总负余量 | 0 / 0 | 0 / 0 |

数据保持/恢复/移除“报告最小值”基于保存的报告路径；全局 HWNS 取工具汇总，以移除检查的 +0.003 ns 为最差。原报告包含 TD 默认 0.100 ns 时钟不确定性。数值为正但最小裕量很小，不能写成“所有时序完美、任何板卡永远不会错”。BASE 使用 12800 LUT，720p 12867 LUT；均为 56/64 块 BRAM、12/29 DSP、2/4 PLL。

用户提到的 −5.08 ns 没有原始起点/终点报告，无法确定是哪个工程或哪类检查。若为 slack，则约 5 ns 违例很大，可能导致随机错字、错色、条纹；若为 PLL 相位参数，必须结合采样关系解释。不能据此认定官方 IP 有一个无法修复的固有问题。本集成工程原 125 MHz 的存储边界曾报告负余量；当前沿用前版 40 MHz 存储时钟、SDRAM 上升沿后移 10 ns，在真实布线后两种模式均无报告负路径。这是当前工程的证据，不代表所有官方 IP 配置都已验证。

如果真实板卡仍报存储错误，优先核对新位流身份及 `PH/BAD/EXP/GOT`，再定位写出、读回采样、刷新、供电和具体引脚，而不能直接删除访问时间或屏蔽 DQ 路径。对组合路径采用真实流水线，对跨域控制采用同步器/邮箱，对 SDRAM 边界采用频率/相位及器件/板级预算，对无法访问的加密内部路径保留报告并联系原厂。这些方法需依据具体失败路径使用。

时序健康报告仍有 6 项无输入延迟、14 项无输出延迟，涉及按键/复位、SD、UART、DDC、TMDS 等外部口；缺少实测板级预算，不能用猜测数字填成“全绿”。没有缺失时钟、非法约束、组合环或被遮蔽的例外。原始 `route.check`、`route.timing`、`route.clocks`、`route.exceptions`、`route.derived.sdc` 均随包交付。

先下载 BASE，串口 115200/8N1 应出现 `SV-MEM ID=26101002`。将交付的四个 640×480、24 位、无压缩 BMP 放入现有 FAT32 卡根目录；无需格式化。先等待首图完成写入/读回，健康帧应有 `PH=2 W=00025800 B=0960`；用 KEY2 切换四幅不同图片，再按住 KEY4 观察连续播放，释放停止继续切换。KEY3 手动黄色 Exit，KEY1 公共复位；故障锁存时为红色 Exit，KEY1 后必须重新完成写入和校验。CONFIG1 重载哪个版本取决于配置 Flash，JTAG 临时下载不会自动更新 Flash。

`PH=3` 是发布前的源/读回/超时失败，`PH=4` 是发布后的播放校验/超时失败；`BAD` 为首个坏块字节地址，`EXP/GOT` 为对应期望/实际 CRC（源地址失败时为地址）。超时的 GOT 可能是先前块结果，应结合第一行状态判断，不视为完整超时块 CRC。完整性检查起点在已经接受的解码源字，不能单独证明更上游的 SD 接收字节没有错误；原 SD CRC16 错误处理继续保留，其效果需在真实卡和串口状态上确认。

尚未执行真实板卡下载、长时间连续播放、不同卡/显示器、电压温度变化。完整卡仿真里的 SDRAM 为应用接口契约模型、HDMI 编码核为契约模型；独立 PHY 用例覆盖可读原厂 PHY/ODDR，未把加密编码或 SDRAM 内部逻辑登记成动态仿真通过。A/B 已实现功能按上面的范围验证；板级正常路径仍关闭 OSD、PCM 静音，未集成的 C/音频调度/UART RX 等规划项不能冒称已完成。真正板卡验收需要下载本版并观察这些结果，无法由电脑端测试作“上板必然正确”的保证。
