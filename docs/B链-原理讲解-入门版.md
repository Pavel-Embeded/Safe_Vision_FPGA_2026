# B 链 · 原理讲解（入门版）

> 读者假设：学过一点数字电路（知道高低电平、时序逻辑、触发器），但没碰过 FPGA 项目。
> 目标：读完能用自己的话讲清"一个字节是怎么从 SD 卡变成屏幕上的像素"。
> 关联：[interface_spec.md](interface_spec.md)（接口细节）、[B链-待办与硬件验证清单.md](B链-待办与硬件验证清单.md)（动手清单）

---

## 一、我们在做什么

最终目标是：**插一张 TF 卡，板子把卡里的图片显示到显示器上，并且出声**——出的是 HDMI 接口里的声音，不是板子上小喇叭的声音。

这件事被切成三条链，B 负责其中一条：

```
        ┌─────────────────────── 你负责的 B 链 ───────────────────────┐
TF 卡 ──┤ 读扇区 → 找文件 → 检查图片是否合法 → 变成像素 → 存进内存      ├──▶ 交给 A 显示
        └────────────────────────────────────────────────────────────┘
```

A 负责把像素变成 HDMI 信号，C 负责按键、状态机和故障处理。

---

## 二、为什么偏偏要用 FPGA

用树莓派塞一张图到屏幕上，十行 Python 就够了。为什么还要折腾 FPGA？

因为**赛题的评分重点是"确定性"**：

- FPGA 没有操作系统，没有"这会儿在干别的"这回事。你写下的时序就是硬件真的会做出来的时序。
- 一次像素输出用掉多少纳秒，是可以算出来的；不会因为后台进程抢 CPU 就抖动。
- 同时，FPGA 能"并行"——B 链在从卡里搬数据的同时，A 链可以同时在往屏幕上刷像素，互不等待。

代价是：**你得自己管一切**。没有文件系统库、没有 `fopen`、没有内存分配。所有东西都要用硬件逻辑一块一块搭出来。这就是 B 链的工作量来源。

## 三、第一层：FPGA 眼里的 SD 卡不是"文件"，是"扇区"

你可能习惯这样想：卡里有个文件夹，里面有 `SV0001.BMP`，双击就打开了。

**但 FPGA 完全看不到这些。** 它看到的是一块一块固定大小的"砖"，每块 **512 字节**，编号从 0 开始。这个编号叫 **LBA（逻辑块地址）**。

> 类比：把 SD 卡想成一栋图书馆。
> - **扇区** = 书架上一个个固定大小的格子（每格正好 512 字节）
> - **LBA** = 格子的编号
> - **"文件"** = 图书馆管理员脑子里的概念。他记录着"《SV0001.BMP》这本书占用了 1000 号、1001 号、9281 号三个格子"
>
> FPGA 是刚来的搬书工：**只认格子号，不认书名**。

那"书名 → 格子号"这本账在哪？就写在卡上，叫 **FAT32 文件系统**。它是几个固定位置的格子：

| 位置 | 存了什么 |
|---|---|
| 第 0 号格子（DBR） | 这张卡的"身份证"：每格多少字节、每簇几个格子、账本从哪开始 |
| FAT 表 | 一张巨大的链表：第 1000 号格子的"下一格是几号" |
| 根目录区 | 一格一格的书名清单，每条记录写着"文件名 + 首格号 + 文件多大" |

**关键认知**：目录里只告诉你"这本书从 1000 号格子开始"，**不告诉你有几格**。想知道全貌，必须去 FAT 表一格一格跳：1000 → 1001 → 9281 → …… 直到遇到一个特殊标记表示"到此结束"。

> 这也解释了为什么手册把 FAT32 列为 B 链工作量最大的一块：你得亲手把这个"跳格子"的过程写成硬件状态机。

## 四、第二层：FPGA 怎么跟卡说话——SPI

FPGA 要跟卡交流，得先解决"怎么接线"。

最简单粗暴的方式叫 **SPI**：用 **4 根线**：

| 线 | 名字 | 方向 | 干什么 |
|---|---|---|---|
| CS | 片选 | FPGA → 卡 | 拉低表示"我在跟你说话"，别人别插嘴 |
| SCLK | 时钟 | FPGA → 卡 | 由 FPGA 产生，节拍器 |
| MOSI | 主机发 | FPGA → 卡 | 一位一位发数据 |
| MISO | 从机发 | 卡 → FPGA | 一位一位收数据 |

**注意一个反直觉的点**：数据不是"一根线一次传 8 位"，而是**一位一位传**。

> 类比：两个人隔着一堵墙传纸条，墙上只有一个硬币大小的洞。
> 一张 8 个字的纸条，得撕成 8 次递过去。每递一次，就"打一拍节拍器（SCLK 跳一下）"。

所以 FPGA 需要两个小电路：

1. **发送**：把 8 位数拆成 8 次一位一位推出去（移位寄存器，先推最高位）
2. **接收**：把收到的一位一位拼回 8 位（也是移位寄存器，先收到的落在最高位）

**"先推最高位"这件事必须写死**，写反了收到的每个字节都是乱码——这是新手第一条常见坑。

节拍器（SCLK）也有讲究：**在哪一拍取值？** 这由两个参数决定（CPOL/CPHA）。SD 卡固定要求"**空闲时 SCLK 为低，在上升沿取值**"。如果取在下降沿（正在跳变的瞬间），就会取到不稳定的电平。

## 五、第三层：跟卡说话其实是在"下命令"

SPI 只是打电话的通道，打通了还得讲同一种语言。SD 卡的语言是**命令 + 响应**。

发命令的格式固定是 **6 个字节**：

```
第 1 字节：0x40 | 命令号        ← 0x40 是个固定前缀，低 6 位是"我要办什么事"
第 2~5 字节：参数（4 字节）      ← 比如"我要读第几号格子"
第 6 字节：校验码              ← 只有少数几条命令真的会被检查
```

卡收到后回一个字节叫 **R1**。R1 的**最高位一定是 0**——所以 FPGA 判断"卡回话了没有"的方法非常简单：**收到的字节最高位是 0 就是回话了，全是 1（0xFF）就是还没回**。

> 这个判断依据很重要：卡在忙的时候 MISO 会一直输出高电平，看起来就像一直在收到 0xFF。

### 开机时要说的话（初始化）

卡刚上电时什么都不认。必须先跟它"对暗号"：

| 顺序 | 命令 | 目的 | 类比 |
|---|---|---|---|
| 0 | 先空发 74 个以上节拍 | 让卡内部电路稳住 | 敲门让人醒一醒 |
| 1 | **CMD0** | 让它进入"待命"状态 | "请出示证件，我要办业务" |
| 2 | **CMD8** | 问它"你是新型卡还是老卡？电压支持哪种？" | "你是新版的还是老版的？" |
| 3 | **CMD55 + ACMD41** | 反复问"你准备好了吗？"，直到它说准备好了 | "好了吗？…好了吗？…好了！" |
| 4 | **CMD58** | 问它"你的容量有多大？是按格子编号还是按字节编号？" | "你是按格子数还是按字节数记账？" |

第 4 步的回答决定了后面一件很重要的事：

- **SDHC / SDXC 卡（大容量，现在基本全是这种）**：地址填**格子号**（LBA）
- **SDSC 卡（老式小容量）**：地址填**字节偏移**，要自己乘 512

搞错这个，读出来的位置会差 512 倍。

### 读一个格子的完整流程（CMD17）

```
1. 发 CMD17，参数填格子号
2. 等卡回 R1（最高位变成 0，且值为 0x00 表示"没问题"）
3. 等卡发来一个"开始标志字节" 0xFE     ← 这一步最容易被忽略！
4. 连续收 512 个字节                    ← 这才是真正要的数据
5. 再收 2 个字节的校验码（CRC16）
```

**三个必踩的坑**（手册也反复强调）：

- **坑 1：把 0xFE 当成数据**。这个字节是"我下面要开始发数据了"的通知，不是数据本身。当成数据的话，512 字节会整体错位一个字节。
- **坑 2：忘了收最后那 2 字节 CRC**。不收的话，下次读命令的响应位置就全错了。
- **坑 3：地址字节序写反**。4 个字节的参数要**高位先发**（大端）。写反了就会去读一个完全不相干的格子。

我们写了 **CRC16 校验**（一种算校验和的算法）来检查这 512 字节有没有传输错误。它的原理很简单：把 512 个字节逐个"揉"进一个 16 位寄存器，最后得到一个 16 位数，跟卡发来的 2 字节比对。对不上说明传输中出了错。

## 六、第四层：BMP 图片文件长什么样

找到了格子，读出来一串字节——但这些字节怎么变成图像？

**BMP 是最"笨"的图片格式**，它的设计哲学是"不做任何压缩，就是把每个像素的颜色原样排好"。所以它最容易用硬件解析。

一个 BMP 文件大致是这样：

```
┌──────────────────────────────────────────────┐
│ 头部（54 字节）                                │
│   前两个字节是 "BM" 两个字         ← 签名，证明这是 BMP │
│   宽 640、高 480                              │
│   每个像素多少位（我们要 24 位 = 3 字节）        │
│   压缩方式（必须是"不压缩"）                     │
│   像素数据从第几个字节开始                       │
├──────────────────────────────────────────────┤
│ 像素数据                                       │
│   B G R  B G R  B G R ……   ← 每个像素 3 字节    │
│   （注意顺序是蓝绿红，不是红绿蓝！）              │
└──────────────────────────────────────────────┘
```

**几个必须注意的点**：

1. **签名必须是 "BM"**。不是就说明这不是合法 BMP（可能是 JPG 改的后缀），必须跳过而不是硬着头皮解析。
2. **颜色顺序是 BGR，不是 RGB**。这是最经典的红蓝颠倒 bug 来源。
3. **每行字节数要补齐到 4 的倍数**。640 像素 × 3 字节 = 1920，正好是 4 的倍数，所以这个尺寸不用补。但**代码里必须按公式算，不能写死**——万一以后换分辨率就错了。
4. **高度可以是负数**。正数表示"图片是从下往上存的"，负数表示"从上往下"。不处理的话图片会上下颠倒。
5. **每个像素 3 字节，但屏幕通常用 2 字节表示**。BMP 用的是"每通道 8 位"（R8 G8 B8），而我们最终要显示成 **RGB565**（红 5 位、绿 6 位、蓝 5 位，共 16 位 = 2 字节）。所以要做一个"降位"转换。

> 为什么要降到 565？省一半内存和带宽。人眼对绿色最敏感，所以绿色多给 1 位。

## 七、第五层：为什么中间一定要有 SDRAM

你可能会想：从卡里读出来直接送到 HDMI 不就行了？

不行，因为**两个速度对不上**：

- SD 卡读数据是"**憋半天，突然来 512 字节，然后又憋半天**"——典型的突发式
- HDMI 输出要求"**每个像素时钟必须准时吐出一个像素**"，一秒都不能停

> 类比：一边是"不定时送货的快递"，一边是"流水线上每 40 纳秒必须来一个零件"。
> 中间必须有个**仓库**来缓冲。这个仓库就是 **SDRAM**（板上的 8MB 内存）。

SDRAM 在这里的角色叫**帧缓存（Frame Buffer）**：先把一整张图完整写进去，再让显示器慢慢地、均匀地读出来。

### 双缓冲：为什么需要两块地方

如果只有一块地方：显示器正在读第 N 张图，你去把第 N+1 张图写进去——那屏幕上半部分还是旧图、下半部分已经是新图，画面就"撕裂"了。

解决办法是**准备两块地（乒乓缓冲）**：

```
块 A：正在显示         块 B：正在写入下一张
        ↓ 写完了，在"垂直消隐期"切换
块 A：闲置             块 B：正在显示
```

**为什么必须在"垂直消隐期"切换？** 显示器扫完一整屏后，有个很短的间隙（垂直消隐）才开始下一屏。这个间隙里屏幕不显示任何东西，**是唯一可以安全换画面的时机**。在画面扫到一半时换，就会出现"上半屏旧图、下半屏新图"。

## 八、第六层：为什么到处都在提 FIFO 和"跨时钟域"

这一条是 FPGA 项目里最容易出事、也最难查的地方，值得单独讲。

看这条链上同时存在几个不同的时钟（节拍器）：

| 时钟 | 频率 | 谁在用 |
|---|---|---|
| `sys_clk` | 100 MHz | SD 卡、文件系统解析 |
| `mem_clk` | 125 MHz | SDRAM 读写 |
| `pixel_clk` | 25.175 MHz | 屏幕像素输出 |
| `audio_clk` | 12.288 MHz | 音频节拍 |

**问题来了**：`sys_clk` 域里产生的一个信号，`pixel_clk` 域能直接拿来用吗？

不能。因为两个时钟**完全独立、没有任何固定关系**。一个信号在 A 域里持续 10 纳秒，对 B 域来说可能是"刚刚好采到"、"采到一半"、或者"完全没采到"——这叫**亚稳态**，表现出来就是"偶尔抽风"：跑一小时错一次，且无法复现。

> 类比：两个人在不同节奏地眨眼。A 睁眼的瞬间，B 可能正在闭眼、正在睁、正好睁全。你没法预测，也就没法保证信息传对。

**标准解法有两个**：

1. **异步 FIFO**（数据通道）：一块能"两头各按各的节奏读写"的缓冲区。写侧按 A 的节奏塞进去，读侧按 B 的节奏取出来。中间的记数指针用专门的同步电路处理。
2. **toggle 电平翻转**（控制信号）：要跨域传"一件事发生了"，**不要发一个单拍脉冲**（太窄，对面可能漏掉），而是把一个电平**翻转**过去（0→1→0→1），对面看到变化就知道"又发生了一次"。

这也解释了几个设计决定：

- 为什么像素数据要经过一个 **FIFO** 才能进 HDMI（跨 `mem_clk` → `pixel_clk`）
- 为什么帧切换握手用 **toggle** 而不是脉冲
- 为什么多比特的数据（比如槽编号）要**先锁存再给回执**，而不能逐位打拍跨域

### FIFO 的两种读出方式

FIFO 有两种常见模式，差别在"数据什么时候出现在输出端"：

| | **FWFT（Show-Ahead）** | **同步读（Normal）** |
|---|---|---|
| 数据什么时候有 | 只要不空，数据**已经在**输出端 | 必须拉 `re` 后下一拍才出现 |
| 读取信号的含义 | "我确认要这个了" | "请把下一个给我" |
| 用了之后 | 逻辑简单，`数据有效 = 不空` | 必须**提前**若干拍发请求，否则行首缺像素、画面整体右移 |
| 风险 | 忘了拉 `re`，会一直输出同一个像素 | 提前量算错，画面错位 |

我们选 **FWFT**，理由是它从结构上消灭了"画面整体右移"这类最难查的故障。代价是**仍然要看水位**：FIFO 空了就会输出重复数据或者黑边。

## 九、完整走一遍：一个字节的旅程

把上面的层次串起来，跟着一个字节走一趟：

```
① 上电
   板载晶振给 FPGA 一个 50MHz 时钟
   PLL（锁相环，一种"倍频器"）把它变成 100MHz / 125MHz / 25MHz 等几路
   每个时钟域等本域 PLL 锁定后，才经本域复位同步器放开该域复位；其他域可独立恢复

② FPGA 跟卡对暗号
   CMD0 → CMD8 → 反复 ACMD41 → CMD58
   结论：这是一张 SDHC 卡，按格子号寻址

③ 读"图书馆的账本"
   读 0 号格子 → 知道每格 512 字节、每簇几个格子、FAT 表在哪
   读根目录 → 翻出一条条记录，找到 SV0001.BMP
   拿到它的首格号和文件大小

④ 查 FAT 表，把这本"书"占的所有格子串起来
   1000 → 1001 → 9281 → …… → 结束标记

⑤ 逐字节读出来，同时做两件事
   - 检查头部：签名是 BM 吗？宽高是 640×480 吗？位深是 24 吗？不合法立刻放弃这个文件
   - 转像素：BGR 三字节 → RGB565 两字节
   （每行末尾如果有填充字节，丢掉）

⑥ 写进 SDRAM 的某个"格子"（我们划了 4 块，对应 4 张图）

⑦ 一整张写完，算个校验和确认没写坏，然后挂上"这块可用"的牌子
   ★ 牌子没挂上之前，绝对不允许显示器去读它——这条规则把"半张图被显示出来"在结构上排除了

⑧ 通知 A："新图准备好了，在下一次屏幕扫完的那个间隙换过去"

⑨ A 在垂直消隐期把显示源切到新块
   从此每个像素时钟从新块里取一个像素，送进 HDMI 变成屏幕上的颜色
```

## 十、术语速查

| 术语 | 一句话解释 |
|---|---|
| **扇区 / LBA** | 卡上固定 512 字节的一块砖 / 这块砖的编号 |
| **FAT32** | 记在卡上的"书名 → 格子号"账本格式 |
| **簇（Cluster）** | FAT32 分配空间的最小单位，等于若干个扇区 |
| **SPI** | 一种 4 线、一位一位传数据的通信方式 |
| **CS / SCLK / MOSI / MISO** | SPI 的四根线：片选 / 时钟 / 主发从收 / 从发主收 |
| **MSB first** | 先传最高位（SD 卡在 SPI 模式下固定这样） |
| **CPOL / CPHA** | 时钟空闲电平 / 在第几个边沿采样；SD 固定 mode0 |
| **R1** | 卡对命令的一字节回应；最高位为 0 表示"回话了" |
| **ACMD** | 需要先发 CMD55 前缀的应用类命令（如 ACMD41） |
| **数据令牌 0xFE** | 卡说"我开始发数据了"的通知字节，不是数据 |
| **CRC16** | 一种校验和算法，用来检查 512 字节传输有没有出错 |
| **BMP** | 一种不压缩的图片格式，头部 54 字节 + 原始像素 |
| **RGB565** | 用 16 位表示一个颜色：红 5 + 绿 6 + 蓝 5 |
| **帧缓存** | 存一整屏像素的内存区域 |
| **双缓冲 / 乒乓** | 一块显示、一块写入，防止画面撕裂 |
| **垂直消隐期** | 屏幕扫完一屏后的空隙，唯一能安全换画面的时机 |
| **时钟域（CDC）** | 两个独立时钟各自管辖的范围；跨域必须有专门处理 |
| **亚稳态** | 跨域传信号时"采到一半"的不可预测状态 |
| **异步 FIFO** | 两头各按各的节奏读写的缓冲区，用于跨时钟域 |
| **toggle 握手** | 用"电平翻转"而不是"脉冲"来跨域传递事件 |
| **FWFT** | FIFO 的一种模式：不空时数据已经出现在输出端 |
| **PLL** | 锁相环，把输入时钟变成几路不同频率的时钟 |

## 十一、几个常见疑问

**Q：既然是读一个文件，为什么不一次读进来，非要分成"找文件 / 查簇链 / 读数据"三步？**
A：因为硬件没有"临时变量"和"递归"。每一步都要先弄清上一步得到的信息才能进行下一步，只能用状态机一步一步走。另外卡的读取速度慢，一次读一大段再处理会占掉太多缓冲。

**Q：为什么超时这么重要？**
A：如果没有超时，卡一旦没插好或者坏了，状态机就会永远等下去——硬件上等于**永久死机**，只能断电重启。这在比赛现场是致命的。所以每个"等外部回应"的状态都必须有独立的超时出口。

**Q：为什么每个等待状态的超时值要分开算？**
A：因为它们的合理量级差几个数量级：等一条命令响应只要几十微秒，等一次数据可能上百毫秒，等卡上电完成可能要一两秒。用一个共同的超时值，要么误杀正常操作，要么等太久失去意义。

**Q：为什么不能直接把参考例程拿来交？**
A：赛题指南明确要求"提交作品的整体实现架构、音频和图片处理方法不能和参考实例相同"。参考例程只能当学习脚手架。

**Q：仿真都过了，为什么还要上板测？**
A：仿真里的卡是"理想卡"——它立刻响应、校验和永远正确。真实的卡上电可能要几百毫秒、不同品牌行为差异很大、且会因为信号完整性（走线、上拉电阻）出现仿真里根本不存在的错误。所以超时值必须上板实测后才能冻结。

## 十二、下半程：从"读到文件"到"画面能上屏"（阶段 8–16）

第九章那条"一个字节的旅程"里，第 ⑤ 步之后就到了 SDRAM。这一章把中间那几层拆开讲。

### 12.1 为什么中间必须夹一个 FIFO（阶段 8）

先看两个速度的真实形状：

| | 形状 |
|---|---|
| SD 卡读 | 等…等…等…**突然来 512 字节**…再等… |
| HDMI 输出 | 每个像素时钟**必须**吐出一个像素，一秒都不能停 |

一个"阵发"，一个"恒定"。**平均速率够不代表瞬时够**——这是新手最容易误判的地方。所以中间必须有缓冲区把阵发抹平，这就是 FIFO。

FIFO 上有几个旗标，但**真正有用的是 `almost_full`，不是 `full`**：

- 你等到 `full` 才去反压上游，上游可能已经又塞进来一个字节了 → 丢数
- `almost_full`（比如深度 64、阈值 48）才是"提前一步说别塞了"

所以水位阈值必须**有推导依据**，不能随便填。本项目的做法是：阈值都是 `localparam` 且标注"设计目标，待实测"，等上板用真实波形标定。

还有一个反直觉的点：**FIFO 里"有数据"不等于"这个数据在这一拍有效"**。同步读（非 FWFT）模式下 `rd_en` 拉高后数据至少晚一拍才出现，叠加异步 FIFO 的同步延迟会更晚。老版例程"读地址一到就当作有效像素"就是这么错的，表现是画面整体右移。我们选 **FWFT**（不空时数据已经在输出端）从结构上消灭这个问题，但仍然要看水位——空了就会输出重复数据或者黑边。

**对应模块**：`rtl/common/sync_fifo.v`（同域 FIFO，带 `almost_full/almost_empty/data_count`）、`rtl/common/rv_skid_buffer.v`（切开上游到下游的 `ready` 长组合路径）、`rtl/memory/fifo_health_monitor.v`（记录历史最低水位与 underflow/overflow 次数）。

> 跨时钟域的异步 FIFO 在真实板上用安路的软 FIFO IP，不由我们手写——手写异步 FIFO 是典型的"看起来对、跑起来偶发丢数"，不值得在比赛里冒险。

### 12.2 SDRAM 不是"大号 RAM"（阶段 9）

SRAM 是"给地址就出数据"。**SDRAM 不是**。它内部按 **Bank / Row / Column** 三维组织，访问它像这样：

| 命令 | 干什么 | 之后要等 |
|---|---|---|
| **ACTIVATE** | 把某一行整行搬到灵敏放大器上 | **tRCD** 之后才能读写 |
| **READ / WRITE** | 在已激活的行里按列读写 | 读要等 **CL** 拍才出数据 |
| **PRECHARGE** | 关行、把电荷写回去 | **tRP** 之后才能重新激活 |
| **REFRESH** | 定期刷新防漏电（DRAM 的电容会漏） | 每次占用 **tRFC** |

关键结论有两条：

1. **同一行内连续访问极快**（不用再 ACT/PRE），**跨行必须先 PRE 再 ACT**，开销很大。这直接解释了下一节的"突发传输"。
2. **REFRESH 不可省**。省掉的后果不是"马上错"，而是"跑两小时后偶发一位错"——这是最难查的一类故障。

本项目的边界划得很清楚：**第一版不手写 SDRAM PHY**，直接跑通官方 Demo、用官方 IP wrapper，B 链的边界止于 wrapper 的请求/响应接口和**逻辑字节地址**。业务模块里**禁止出现裸物理地址运算**（否则换 wrapper 版本时全链地址都要改）。这部分对应 `rtl/memory/mem_ctrl.v` + 仿真用的 `verification/models/frame_memory_model.sv`。

### 12.3 帧缓存与地址映射（阶段 10）

一块内存怎么表示一张二维的图？**行优先**：一行一行接着放。

```
字节地址 = 基地址 + (y × 宽 + x) × 每像素字节数
```

代入本题：`slot_base + (y×640 + x) × 2`。

两个最容易错的地方：

- **漏乘"每像素字节数"**。RGB565 是 2 字节/像素，忘了乘就全错位。
- **把"行步长"和"图像宽度"混为一谈**。本题因为 640×2=1280 且没有额外对齐，行步长恰好是 1280 字节；但如果哪天换成宽度奇怪的分辨率，行步长会被对齐规则改变，所以**公式里必须用参数算，不能写死 640**。

容量账（手册 7.12 的表 7-3）：

| 对象 | 容量 |
|---|---|
| 单幅源文件 640×480×24bit | 921,600 Byte ≈ 900 KiB |
| 四幅源文件（在 TF 卡上） | 3,686,400 Byte ≈ 3.6 MB |
| 单槽缓存 640×480 RGB565 | 614,400 Byte |
| 四槽实占（每槽对齐到 0x0A0000） | 2.5 MiB |
| 音频环 | 256 KiB |
| 片内 SDRAM 总量 | 8 MiB |

四槽对齐到 0x0A0000（640 KiB）是为了地址译码简单，代价是浪费一点空间——8 MiB 里还剩约 4 MiB 余量，值得。

**对应模块**：`rtl/memory/frame_address_gen.v`（纯组合的地址计算）、`rtl/memory/frame_writer.v`（写一帧 + CRC 抽检 + 置 `slot_valid`）。

这里有一条**必须背下来的规则**：`slot_valid` 没置位之前，绝对不允许显示侧去读这一槽。它把"半张图被显示出来"这件事在**结构上**排除掉了，而不是靠"小心一点"。

### 12.4 突发传输：为什么不一个像素一请求（阶段 11）

如果"请求一个像素 → 等 → 再请求一个像素"，那么每次都要付 ACT/PRE 的代价，带宽会被开销吃光。

正确做法是一次连续读/写一长串，让 ACT/PRE 的开销被摊薄。已知 SDRAM 一次突发读 64 个 word（256 Byte）塞进 FIFO。

但**突发也不是越长越好**：太长会把另一路（比如帧写入）的等待时间抬高。所以突发长度要和 FIFO 深度、仲裁切换粒度**一起定**，最终判据是 **FIFO 最低水位**。

### 12.5 带宽预算：B 的核心比赛能力（阶段 12）

这一节是评审最爱问的。算账分两边。

**需求侧**（本题 640×480@60）：

```
像素率     = 640 × 480 × 60        = 18.432 MPixel/s
单图显示读 = 18.432M × 2 Byte      = 36.864 MB/s
双图滑动   = 36.864 × 2            = 73.728 MB/s
音频流     = 48000 × 2 × 16bit     = 0.192 MB/s
帧写入     = 614400 ÷ 3s           ≈ 0.2 MB/s
峰值需求   ≈ 74.2 MB/s
```

**供给侧**：

```
理论峰值 = 4 Byte × 125 MHz = 500 MB/s
但这不是结论！刷新 / ACT / PRE / 切换都要吃掉一部分
效率系数 0.6–0.7  =>  有效带宽目标 300–350 MB/s
```

**结论的正确写法**只有一种：**用计数器统计一段时间内实际搬运的字节数，除以时间**，同时给出该时段的 **FIFO 最低水位**。写"理论 500 MB/s，裕量充足"在评审里等于没写。

还有一个容易被忽略的取舍：**即使最终输出画布是 1280×720，显示读流量也不随输出分辨率线性增长**。因为图片是一比一显示在 640×480 画布上，背景、OSD、应急图形都由逻辑实时生成，不从 SDRAM 读整幅 720p 帧。这个取舍在答辩时要主动讲。

**对应模块**：`rtl/memory/memory_bandwidth_monitor.v` + `rtl/memory/fifo_health_monitor.v`。

### 12.6 仲裁：同一时刻谁先读内存（阶段 13）

SDRAM 只有一个口，但有好几个主设备要抢：视频显示读、帧写入、调试通道。

第一版用**固定优先级**：`Video Read > Frame Write > SD`。理由是 HDMI 一刻不能停，读 FIFO 一空就立刻花屏。

但固定优先级有**饥饿**风险（低优先级永远轮不到），所以手册要求**无论用哪种策略都必须加两条硬约束**：

1. 任何一次授权**不允许连续独占超过 N 个突发**
2. 每个主设备有"最长等待时间"计数器，**超限即临时提升优先级**

这两条是本项目答辩时的加分点——它说明我们不是"想当然地用了固定优先级"，而是知道它的缺点并做了防护。

**对应模块**：`rtl/memory/memory_arbiter.v`。

### 12.7 双缓冲与帧交换握手（阶段 14 / 15）

**撕裂（Tearing）**：A 正在读 Frame0，B 同时往 Frame0 写，A 就会读到"写了一半"的画面，表现为**上旧下新的横向错位**。

双缓冲的规则只有一句：**显示永远读一块完整的旧帧，写侧永远写另一块。**

但它不解决"新帧写得太慢导致切换滞后"，所以写入耗时也要纳入验收。

**帧交换**是 B 和 A 的第一次真正协同，也是整条链上最容易出错的一处，因为它跨了两个时钟域。这里有**两种典型错法**：

| 错法 | 后果 | 正确做法 |
|---|---|---|
| 把 `frame_ready` 当**单拍脉冲**打两拍跨域 | 目标时钟可能采样不到，**事件整体丢失** | 用 **toggle 电平翻转**：每次提交把电平翻一下，对面先同步电平、再做边沿检测 |
| 多比特载荷（槽号/代次）**逐位各打两拍** | 取到"半新半旧"的组合值（槽号更新了但代次还是旧的）→ A 读到还没写完的块 | **mailbox 锁存**：写侧先一次性写入整组寄存器并保持稳定，读侧在消隐期载荷稳定后再采样，采样完再给回执 |

帧交换的状态机（手册表 7-6）：

```
IDLE --frame_ready & crc_ok--> WAIT_VBLANK --frame_start--> COMMIT --swap_ack--> WAIT_ACK --> IDLE
   （任意状态超时 -> SAFE：保持当前显示块，置 swap_error 交 C）
```

**为什么必须只在垂直消隐期原子切换？** 因为一帧内像素是按 x、y 连续扫描的。如果在有效像素区中途改了 `active_slot`，同一帧上半部分来自旧块、下半部分来自新块——即使两块图都完整，画面仍是拼接错的。消隐期内像素流水线不输出有效像素，但 TMDS 链路仍在传控制周期，所以对显示器**完全不可见**。

"原子"的含义是：`active_slot` 和它配套的 `slot_base`、`generation` 必须在**同一时刻**一起更新。

**对应模块**：`rtl/memory/frame_swap_ctrl.v`（状态机）、`rtl/memory/frame_swap_cdc.v`（toggle 同步 + mailbox）、`rtl/memory/frame_buffer_manager.v`（槽基地址与所有权）。

### 12.8 错误处理：不能只做正常路径（阶段 16）

赛题明确考察鲁棒性。**B 链必须覆盖的五类故障**，每类都要有检测、重试、上报、降级：

| 故障 | 上报信号 | 硬规则 |
|---|---|---|
| SD 没插 / 被拔 / 初始化失败 | `media_present` / `sd_error` | **立即停止发起新事务，但保留已缓存的图像继续显示** |
| 读扇区超时 / CRC 错 | `sd_error` | 有限次重试后才报错 |
| 目录项 / 簇链校验失败 | `file_error` | 坏图跳过，继续找下一幅（不能因为一张坏图就放弃） |
| FIFO 反压不及时 | `fifo_overflow` | 丢帧并计数 |
| SDRAM 控制器状态异常 | `mem_error` | — |
| 帧交换握手超时 | `swap_error` | **保持当前显示块**，交 C 处理 |

**拔卡时的规则值得单独说**：不是"立刻黑屏报警"，而是"**停新事务、保画面、等重插**"。因为 B04/E04 都要求"画面不能因为媒体路径故障就消失"。

还有一条**能力口径**要守住：只能承诺**媒体路径**故障降级（拔卡、文件损坏、读超时）。FPGA、电源、PLL、HDMI 物理层是全链路共用的，**不能承诺任何单点故障都不黑屏**。写进报告时要按这个口径说，不要吹。

**对应模块**：`rtl/common/error_report.v`（错误事件汇聚，不允许丢弃）+ 各模块自己的 `err_code/err_detail`。

### 13.3 怎么跑仿真

```powershell
$env:MSIM_BIN = "D:\path\to\modeltech64_10.7\win64"
powershell -ExecutionPolicy Bypass -File .\safevision\tools\run_sim.ps1
# 或者：... -File .\safevision\tools\run_sim.ps1 -ModelSimBin <win64目录>
```

ModelSim 的安装目录从 `-ModelSimBin` 参数或 `MSIM_BIN` 环境变量拿，**脚本里不写死任何本机路径**
（换机器只要设这两者之一）。这与 A 的 `run_clock_sim.ps1` 是同一套口径。

脚本会依次编译并运行全部 testbench，每条断言打印 `[PASS]`/`[FAIL]`，最后给出失败项计数。**失败数必须是 0**。

新增模块时，把文件加进 `tools/run_sim.ps1` 的 `$RTL` / `$SIM` / `$TBS` 三个列表即可。
**只把文件放进目录而不加进列表，等于死文件**（曾经真实发生过：两个 CRC 通用件建好了却没进编译列表）。

改完目录或脚本，可以先跑一个**不需要 ModelSim** 的自检：

```powershell
powershell -ExecutionPolicy Bypass -File .\safevision\tools\check_repo.ps1
```

它核对必需目录/文件是否存在，并解析 `run_sim.ps1` 里的 `$RTL/$SIM/$TBS` 引用有没有断链，
输出 `LAYOUT PASS` 才算通过。它查不到"文件建好但没进列表"这类反向问题，所以两个都要跑。

> 脚本里有个坑要注意：**这个 `.ps1` 必须保持纯 ASCII 注释**。PowerShell 5.1 在没有 BOM 时按 ANSI 解码，中文注释会把后面的引号"吃掉"导致解析失败。中文注释写在 RTL 文件里。

### 13.4 接手时要背下来的 7 条约定

这些全是实测踩出来的，不是理论：

1. **从上游收数据必须用 `valid && ready` 双判**。上游会把 `valid` 挂在同一个字节上不放，只判 `valid` 会把同一字节吃掉很多次，字节计数瞬间错位。
2. **"下游取走数据"的清零逻辑要放在状态机之外**，对所有状态生效。否则"最后一个字节被锁存的那一拍正好也是状态跳走的那一拍"，`valid` 再也没人清，直接死等超时。
3. **多字节字段（FAT 入口、BMP 头）是小端**。装配要"新字节从高端进、老字节往低端退"，装反了会把 640 读成 0x80020000 这种数，症状很误导。
4. **字节数够了也不能中途停读**。`sd_sector_reader` 的 `rd_ready` 只在空闲态有效，中途把 `data_ready` 拉低不放它会永远卡住。正确做法是记下"该收工了"，把本扇区收干净再收工。
5. **每个等待外部响应的状态都要有独立的超时出口**，禁止全模块共用一个计数器。没有超时在硬件上等于**永久死机**。
6. **`slot_valid` 未置位不许读那一槽**。这条规则把"半张图进画面"在结构上排除。
7. ★ **一个 `reg` 只能有一个驱动源（一个 `always` 块）**，连复位赋值也算在内。
   这条是 2026-10-02 才补进来的，因为它是**第一次跑 TD 综合才暴露**的：
   `sd_initializer` / `sd_sector_reader` 的 `bdata` 本应只由主状态机驱动，但字节引擎的复位分支
   里也多写了一次 `bdata <= 8'hFF`。**ModelSim 编译和仿真一个警告都不给**（两个 `always` 块写同一个
   `reg`，仿真里只是竞争，"谁最后写谁赢"），所以当时那套单元 TB（507 项断言）照样全绿；而 TD 一 elaborate
   就报 `net 'bdata[7]' is constantly driven from multiple places`，并把整个模块降级成黑盒。
   **推论**：仿真全绿 ≠ 能综合。**改完 RTL 一定要真跑一次 TD 综合**，别只看 ModelSim。
   查法：TD 报的 "found another driver here in 文件(行)"，就是第二个 `always` 块的起始行，
   把那两处对着看，然后把其中一个赋值（通常是复位分支里多余的那次）删掉。

### 13.5 上板的第一件事

不是跑整机，而是 §2.2 里那块"阶段 5 最小验证"：只做 `SD → UART → 电脑逐字节比对`。
**这块的板级顶层已经写好了**：`platform/anlogic_eg4s20_hx4s20c/rtl/top_stage5_sector_rd.v`，
配套 `constraints/pin.adc` 与 `timing.sdc` 也已按原理图核对完，TD 工程里 `TOP_MODULE` 也已指向它。

顶层只做四件事：上电等待 → 初始化 SD → 读 LBA=8192 一个扇区 → 把 512 Byte 从 UART 发出去。
看 LED 就能知道卡在哪一步：`1` 上电等待、`2` 发初始化、`3` 等初始化完成、`4` 发读请求、
`5` 传输中、`8` 成功；其它值表示失败，显示的是错误主码低 4 位。

四个值得知道的设计选择（都不是随便定的）：

1. **全跑 50 MHz，不接 PLL**。板上晶振经 R7 进 FPGA 就是 50 MHz。bring-up 阶段先用最少的
   依赖把链路跑通——PLL 配错、锁不定这类问题会伪装成"SD 读不出来"，先把这一层排除掉。
   代价是 SPI 时钟变慢（初始化段从 400 kHz 变 200 kHz，仍在规范允许的 100–400 kHz 内），
   超时的墙上时间翻倍（只会更宽松）。产品链的 100 MHz 是后面整机集成时 A 用 PLL 的事。
2. **两个 SD 模块共用一条 SPI 总线**。`sd_initializer` 和 `sd_sector_reader` 各自都带一套
   "发字节/收字节"的小引擎，但同一时刻只有一个在动，所以顶层用 `init_done` 做二选一，
   把选中的那一方的 `tx_valid/tx_data` 接到唯一的 `spi_master`。两个都是低有效的片选直接**相与**，
   谁拉低就低、都空闲就高。
3. **UART 比 SD 慢两个数量级，靠 `ready` 顶住**。115200 下一个字节要 87 us，512 Byte 要 44.6 ms，
   而 SD 读一个扇区远快于此。所以顶层的连接就是一句话：
   `uart_tx_valid = reader 的 data_valid & uart 的 tx_ready`，同时 `reader 的 data_ready = uart_tx_valid`。
   两者同拍握手一拍：UART 收下字节后立刻离开空闲态（`tx_ready` 变低），reader 下一拍清 `data_valid`，
   既不会重复发也不会丢。reader 在 `S_DATA` 会停住 SCLK 等下游，而这个状态本身没有超时计数器
   （超时只挂在等响应和等数据令牌上），所以"发得慢"不会被误判成超时。

4. ★ **读哪个 LBA：不是随便挑的，这里藏着一个"看着通过、其实没测到"的坑**。
   原计划读 LBA 1000。但我实测了这张卡：它的**分区从物理扇区 8192（4 MB）开始**，
   所以**物理 LBA 1000 落在"MBR 之后、分区之前"的空隙里，读出来就是 512 个 `0x00`**。
   两边都是全零 → "逐字节比对"几乎证明不了数据通路（数据通路要是坏成常数 0，也会"通过"）。
   所以改成 **LBA 8192 = 分区第一个扇区 = FAT32 引导扇区（DBR）**：内容非零且一眼能认
   （开头 `eb 58 90` + `MSDOS5.0`、结尾 `55 aa`），错一个字节都看得出来。
   电脑侧参考值存在 `evidence/board/lba8192_pc_20261002.bin`。
   **顺带记住两个概念**：
   - FPGA 的 LBA 是**从整张卡开头算的物理块号**；
   - Windows 的**卷句柄（`\\.\G:`）偏移是从分区开头算的**，所以 `\\.\G:` 偏移 0 = 物理
     LBA 8192，而不是 LBA 0。想读物理 LBA，得用「物理磁盘」句柄（要管理员权限）或 HxD 的
     「打开物理磁盘」。用 `\\.\G:` 偏移 512000 读到的**不是** LBA 1000。
   - 要让这个"逐字节比对"真的有意义，**基准扇区的内容必须非零**。

**`uart_txd` 用的是 D12，已经确认过了，不用再猜**：开发板手册的串口引脚表写着
`RXD = F12` / `TXD = D12`；手册图2-10（CH340G 串口原理图）里，CH340 的 pin2（芯片 TXD，输出）
接的是网络 `RXD`，pin3（芯片 RXD，输入）接的是网络 `TXD`——**两根线是交叉的**，这说明网络名
是按 **FPGA 的视角**起的：`RXD`(F12) 是 FPGA 收，`TXD`(D12) 是 **FPGA 发**。
所以 D12 是输出、对方是输入，**不存在两个输出对着顶**的情况。

还有个好消息：**板上自带 USB 转串口（CH340G），不需要另外买 USB-TTL 模块**。
操作就是插一根 USB 线到板上那个 USB 口，在电脑上打开新出现的 COM 口，设 **115200 8N1**，
就能收到 FPGA 发出来的 512 个字节。

**但采集必须用"二进制"方式，这条踩过坑（2026-10-02）**：用串口助手的**文本模式**保存，
得到的文件里会出现一大堆 `EF BF BD`，而且文件比 512 字节还长（实测变成 740 字节）。
原因：`EF BF BD` 是 **U+FFFD（替换字符）的 UTF-8 编码** —— 工具把字节流当成**文本**去解码，
凡是不符合 UTF-8 规则的字节（基本就是 `≥0x80` 那些）都被它换成了这个替换字符，**不可逆**。
也就是说 **512 个字节里有 141 个被毁掉了，再也还原不回来**。

那怎么判断"是 FPGA 发错了"还是"只是保存方式的问题"？有个很干净的判据：
**把参考的 512 字节按同样的规则"当文本解码（非法字节→替换字符）再编码"，如果结果与采集文件
逐字节相同，那就说明 FPGA 发的完全正确，错只在保存方式。** 本次就是这么定案的：
参考变换后得到 740 字节，与采集文件**逐字节完全相同**（`mangled == capture` = True）。

正确的做法：用 `safevision/verification/board/capture_uart_512.ps1`（直接存二进制并自动比对），
或者把串口工具设成 **HEX / 二进制导出**。**别用"文本另存"**。

如果这一步没过，按 [B链-待办与硬件验证清单.md](B链-待办与硬件验证清单.md) §2.6 的排查顺序一条条找，不要跳着猜。
